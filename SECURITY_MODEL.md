# OpenClaw Safe — Security Model

This document defines the threat model, trust assumptions, security
invariants, and enforcement mechanisms for OpenClaw Safe.

It is intended for security reviewers, contributors, and coding agents.
Any change that weakens a stated invariant must be explicitly reviewed
and justified.

---

## 1. Threat Model

### Attacker capabilities assumed

| Threat | Assumed |
|---|---|
| Model outputs are adversarial (prompt injection, jailbreak) | **Yes** |
| User-supplied inputs are adversarial | **Yes** |
| Plugin packages may be malicious | **Yes** |
| Model-generated tool arguments are adversarial | **Yes** |
| Operator-level principal is trusted | Yes (within their policyGroup) |
| System-level principal is trusted | Yes (internal only, never exposed to model) |

### What we do NOT assume

- The model is trusted.
- User inputs are safe.
- Tool arguments generated by the model are correct or benign.
- A high-trust principal cannot make mistakes.

---

## 2. Trust Hierarchy

```
system
  │   (internal orchestration, never exposed to model)
  │
operator (high trust)
  │   (human operators; may use all tool classes with some approval gates)
  │
user (medium trust)
  │   (end users; Class D/E require approval)
  │
user (low trust)
      (restricted to Class A tools only)
```

**child_agent** principals inherit only the capabilities explicitly granted
by the parent task's `capabilitySet`. Child agents cannot escalate trust.

---

## 3. Security Invariants

These invariants must hold at all times. A code change that violates any
of them is a security defect, not a feature.

### 3.1 Every tool execution is policy-evaluated

No tool may execute without a `PolicyEngine.evaluate()` call that returns
a non-deny mode. The policy engine is the single mandatory gate.

**Enforcement**: `ToolBroker.dispatch()` always calls `policyEngine.evaluate()`
before dispatching to a worker. The broker is the only code path that may
call a `WorkerExecutor`.

### 3.2 No tool executes without a broker-issued execution lease

Workers receive an `ExecutionLease` generated by the broker. A worker
that receives a lease it did not request from the broker is not an intended
execution path.

**Enforcement**: `ExecutionLease.id` is a UUID generated by the broker.
Workers are called only by the broker's `dispatch()` method.

### 3.3 The policy engine is pure

`PolicyEngine.evaluate()` is a pure function. It has no database access,
no HTTP calls, no side effects. It takes a `PolicyContext` and returns a
`PolicyDecision`.

**Enforcement**: `src/core/policy.ts` imports only `src/core/types.ts`.
This boundary is checked in CI.

### 3.4 Sandbox is the default runtime

Every tool that does not explicitly require a different runtime target
executes in the sandbox. There is no silent fallback from sandbox to host.

**Enforcement**: `ToolBroker.dispatch()` uses
`decision.allowedRuntimeTarget ?? schema.defaultRuntimeTarget` as the
effective runtime. If no worker is registered for the effective target,
the execution fails with `tool.error`; it does NOT retry with `host_elevated`.

### 3.5 Host elevation requires explicit grant

`host_elevated` runtime is only reached when:
1. The tool's policy effect is `host_elevated_only` (Class F), AND
2. `session.elevationState === true`.

If either condition is false, the broker returns `denied: true`.

### 3.6 Audit log is append-only

Audit records are only inserted, never updated or deleted in the normal
operation path. The SQLite schema has no `UPDATE` or `DELETE` statements
in the `AuditLog` class.

### 3.7 Approval cannot be bypassed

When policy returns `allow_with_approval`, an `ApprovalResolver` must be
invoked and must return `'approved'` before execution proceeds. There is
no code path that proceeds from `allow_with_approval` without a resolved
approval.

If no `ApprovalResolver` is registered, the broker denies the request.

### 3.8 Secrets are never in model context

The model receives only policy-filtered tool schemas and user messages.
Secret values are not injected into the system prompt, user messages, or
tool results by any built-in code path.

### 3.9 Input validation at all API boundaries

All external inputs (HTTP request bodies, query parameters, WebSocket
messages, plugin arguments, model-generated tool arguments) are parsed
and validated using typed schemas (Zod) before use. Raw `unknown` inputs
are never passed to internal functions without validation.

### 3.10 Low-trust principals are restricted to Class A

Principals with `trustLevel: 'low'` are denied any tool with risk class
B, C, D, E, or F by a dedicated policy rule that fires before class-level
allow rules.

### 3.10b Readonly sessions are restricted to Class A

Sessions with `mode: 'readonly'` are denied any tool with risk class
B, C, D, E, or F by a dedicated policy rule that fires before class-level
allow rules.

A plugin may only invoke a capability listed in its `capabilities` manifest field. The gateway enforces this before the `PolicyEngine.evaluate()` call. A capability not in the manifest results in a `plugin.capability.denied` audit event and a 403 response.

The plugin's `riskClass` is used verbatim as `toolRiskClass` in the `PolicyContext`. A plugin cannot self-assign a lower risk class to obtain broader permissions.

### 3.12 Plugins cannot access the DB, audit log, or runtime workers directly

`PluginStore` holds manifest/state data only. It has no reference to `AuditLog`, `ToolBroker`, or any `WorkerExecutor`. The import boundary check enforces this at the package level (`plugins/*` must not import `core/broker`, `core/audit`, `core/session`).

### 3.13 Delegation cannot widen capabilities or budget

When a parent task delegates to a child, the child's `capabilitySet` is intersected with the parent's. The child's `budgetCap` must not exceed the parent's remaining budget. Both constraints are enforced atomically in the delegate route; violation results in a 400 and an audit event.

### 3.14 Delegation depth is capped at 5

`MAX_DELEGATION_DEPTH = 5`. Attempts to exceed this emit `delegation.depth.exceeded` and return 400. The child count per parent is also capped at `MAX_CHILDREN_PER_TASK = 20`.

## 4. Policy Rule Evaluation Order

Policy rules are evaluated in order; the **first matching rule wins**.

The default ruleset enforces this ordering:

1. `system-allow` — system principals bypass trust-level checks.
2. `readonly-session-deny-writes` — readonly sessions blocked from B–F
   (must come before class-level allow rules).
3. `low-trust-deny-non-readonly` — low-trust principals blocked from B–F
   (must come before class-level allow rules).
4. `class-f-require-elevation` — Class F always host_elevated_only.
5. `class-e-medium-low-approval` — Class E requires approval for non-high-trust.
6. `class-e-high-allow` — Class E allowed for high-trust.
7. `class-d-medium-low-approval` — Class D requires approval for non-high-trust.
8. `class-d-high-allow` — Class D allowed for high-trust.
9. `class-c-sandbox-only` — Class C sandbox-only.
10. `class-b-sandbox` — Class B allowed in sandbox.
11. `class-a-allow` — Class A always allowed, audit not required.
12. `default-allow` — catch-all allow with audit.

Rules 2 and 3 **must** appear before rules 4–12. If they are moved after
the class-level rules, low-trust and readonly restrictions are silently bypassed.

## 5. Forbidden Patterns

The following patterns are explicitly prohibited. Any code introducing
them must be rejected at review.

| Pattern | Why |
|---|---|
| Agent or gateway calling `worker.execute()` directly | Bypasses policy engine and audit log |
| Gateway route that invokes tools without the broker | Bypasses capability check and approval gate |
| Plugin executing host commands directly | Bypasses sandbox isolation |
| Silent sandbox → host fallback | Silently escalates privilege |
| Skipping approval because the principal is "trusted" | All code paths must be consistent |
| `eval()` or `new Function()` in control plane code | Remote code execution risk |
| Wildcard allowlists (`*`) for network domains | Removes network isolation |
| Logging secret values or sensitive params | Secret leakage |
| Expanding `capabilitySet` to make tests pass | Masks real security boundaries |
| Casting `unknown` inputs without validation | Input validation bypass |

## 6. Approval Enforcement Details

Approval requests carry:
- `riskClass`: must match the tool's declared class.
- `duration`: `once | session | task | policy_rule`.
- `humanReadableDiff`: mandatory human-readable description.

An approval with `duration: once` is consumed by a single tool invocation.
An approval with `duration: session` persists for the session lifetime.
An approval with `duration: task` persists until the task completes.
An approval with `duration: policy_rule` adds a permanent rule (operator only).

Expired approvals (`outcome: 'expired'`) are treated identically to denied.

---

## 7. Audit Requirements

For every broker dispatch that results in execution, the following events
must appear in the audit log (for tools with `auditRequired: true`):

1. `tool.started` — emitted before worker execution.
2. `tool.finished` or `tool.error` — emitted after worker execution.

For denied dispatches:

3. `tool.denied` — capability set denial.
4. `policy.denied` — policy engine or approval denial.

For approval flows:

5. `approval.requested` — when an `ApprovalRequest` is created.
6. `approval.resolved` — when an `ApprovalRequest` is resolved.

No silent execution path exists. If an event is not in the audit log,
it did not happen through the intended code path.

## 8. Sandbox Security Properties

The `SandboxWorker` provides:
- **Ephemeral workspace**: per-invocation temporary directory.
- **Minimal environment**: only `HOME` and `TMPDIR` are set; no PATH, no credentials.
- **Wall-clock timeout**: configurable `timeoutMs`, default 30 seconds.
- **Output cap**: stdout + stderr capped at 1 MiB.
- **No ambient network**: child processes have no network access by default.
- **Filesystem diff capture**: changes to the workspace are recorded.

The sandbox does **not** currently use OS-level namespaces (cgroups, seccomp,
containers). Production deployments should wrap the sandbox in OS isolation
appropriate to the threat model.

---

## 9. WebSocket Event Stream

The gateway emits structured events over WebSocket. Access requires a
bearer token (`gatewaySecret`). Connections from non-loopback addresses
are rejected by default.

Events do not include secret values or full audit payloads; they carry
only identifiers and status codes. Full audit data is available only via
the authenticated `/v1/audit` endpoint.

---

## 10. Definition of Security-Complete

A change is security-complete only if:

- All invariants in §3 are preserved.
- No forbidden pattern from §5 is introduced.
- New tool paths emit the required audit events from §7.
- New principal types or trust levels are covered by policy rules that
  fire in the correct order (§4).
- Tests explicitly cover denial paths, not just happy paths.
- The audit trail for new code paths is complete and verifiable.
